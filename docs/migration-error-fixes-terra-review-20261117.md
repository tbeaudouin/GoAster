# Migration error fixes independent review — 2026-11-17

## Findings

1. **High: provider error classification can erase a confirmed or uncertain creation outcome.** `internal/migration/oneshot.go:287` changes even an explicit `created` or `unknown` response to `not_created` solely from HTTP 422, stage and either error code. `SanitizeOneShotResult` repeats this at line 144, including on operation results and persisted metadata. Conversely, lines 147–148 and 290–291 change even an explicit `created` response to `unknown` for a timeout code. A contradictory response can therefore discard the strongest evidence of a server and cause incorrect reconciliation advice. The documented contract also says `not_created` means no server-create request was dispatched, which a provider 422 by itself does not establish (`docs/api-first-web-contract-20261116.md:17`). Preserve confirmed `created` and uncertainty unless the authoritative service contract establishes a safe outcome; treat contradictory combinations as unusable or conservatively preserve the stronger state. Align the contract's definition with the actual service semantics. Add cases for `created` and `unknown` with 422/invalid_input and for `created` with timeout, through both Web decoding and tool sanitization; the current 422 test instead asserts that an explicit `unknown` is downgraded.

2. **High: valid accumulated metadata can disappear entirely from model context.** `internal/chat/migration_diagnostics.go:178` marshals all eight allowed records, then returns an empty notice if their combined JSON exceeds 8 KiB. Each record may contain eight fields with eight allowlisted messages, so independently valid records can exceed the aggregate limit. `internal/chat/provider.go:768` then supplies no diagnostic notice at all, including no latest creation outcome or uncertainty, despite retaining the records on disk. Enforce the aggregate budget when accumulating or rendering, retaining at least the newest outcome and preferentially trimming older records/details; ensure the notice itself is included in the bound. Add a multi-record, maximum-valid-details test that verifies the latest outcome remains in follow-up context after restart.

3. **Medium: deduplication destroys the ordering of repeated outcomes across attempts.** `internal/chat/migration_diagnostics.go:119` discards any record equal to an earlier record, even after a different outcome. For example, `unknown`, `not_created`, `unknown` is presented as `unknown`, `not_created`; there is no attempt identifier or timestamp in these records to indicate that the latest result was uncertain. This matters especially after a failed turn, when the user/assistant messages for the latest attempt are intentionally absent. Retain occurrence order, or move a repeated record to the end and make the ordering semantics explicit. Add a failed-turn/restart regression with repeated outcomes separated by a different outcome.

## Scope and verification

The findings above limit the safety of the resulting context and creation-state semantics.
