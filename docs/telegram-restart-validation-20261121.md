# Telegram restart validation — 2026-11-21

Review found that the original guard held a global lock after failed handoffs, blocked incoming chat requests, and did not account for known background processes. The adapter also had an admission race and only suppressed stale restart commands in the first poll. These paths have been corrected.

The paired account can send bare `/restart` without attachments. The adapter rejects active or queued Telegram work. The authenticated agent guard rejects active chat, dispatched cron work, and running, stopping, or unrecognized manager-owned background sessions. Guarded cron attempts use the scheduler's retry path without consuming a run. The finite guard lease covers acknowledgement; an authenticated commit disables expiry before systemctl starts. A proven pre-dispatch failure releases the guard. An uncertain command outcome or lost commit response keeps admission blocked and asks for manual service status verification; no automatic recovery or replay is attempted. Process exit clears the old process guard.

After acknowledgement, the adapter invokes `systemctl restart goaster-agent.service` once, with a 30-second deadline. Successful command completion is followed by a bounded health check; readiness timeout is logged and reported. Telegram restart messages dated at or before adapter startup are discarded on every poll, including beyond the first 100 updates; the initial poll is also discarded for restart commands. Telegram timestamps have one-second precision, so a restart sent during the startup second is conservatively discarded. Duplicate restart commands in one poll are suppressed. Messages arriving during the handoff may be rejected and should be resubmitted. Histories and credentials are retained.

Offline tests use fake Telegram, agent, manager, and restart functions; no live service, systemctl command, or API was invoked. They cover authorization, arguments, active and queued work, guard authentication, background work, release, expiry, concurrent admissions, acknowledgement and command failures, non-systemd and unavailable guard, health timeout, duplicate commands, and a stale command beyond the first page.

Offline verification: the complete affected Telegram, command-catalog, and agent suites passed with the known baseline `TestAgentPromptUsesRuntimeSkillsAndMemorySetup` excluded. Focused restart tests passed under the race detector; `go vet ./...`, `go build ./cmd/...`, and `git diff --check` passed. The excluded baseline expects `# Memory guidance`, which is absent from the current starter memory fixture. No deployment or live restart was performed.

No live systemd unit configuration, deployment topology, service command, Telegram delivery, or restart was verified. Readiness reporting depends on the Telegram adapter remaining alive independently of the agent service. Only manager-owned background sessions are checked. Manual intervention may be needed to restore availability after an uncertain outcome.

Additional offline regressions reload refused one-shot and MaxRuns-limited recurring jobs from disk and verify each executes once after the guard releases. A mocked stopping session exercises the known-state admission check. Diagnostic tests cover HTTP, missing-response and command classifications, malicious request IDs and errors, and single-owner send logging. A fake command timeout followed by later completion verifies that restart and new work remain blocked pending manual recovery. Systemd checks and command start failure are simulated without running systemctl. These tests do not validate a real manager or systemd job.
