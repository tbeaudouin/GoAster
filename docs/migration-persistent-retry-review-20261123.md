# Persistent migration retry review — 2026-11-23

The error-after-result regression is resolved. A nonterminal migration result can retain its scheduled retry after a positively identified provider HTTP or stream failure with completed tools. Unclassified errors, handler and local persistence failures, interrupted actions, and compound failures that cannot be safely classified require review. A call to any unrelated tool during the turn also requires review if the turn later fails, even when that tool returned successfully. The observer records only tool names and preserves any existing observer. Some provider failures that lack sufficient typed evidence conservatively require review.

The earlier findings about approved parameters and pre-attempt self-disable describe existing instruction-led trust boundaries. Ordinary cron instructions tell the model to use the approved literal parameters and terminal conditions; the runtime does not bind those parameters to an approval or recognize a special migration job before the migration tool is called. A model that disregards the instructions can alter parameters, disable before an attempt, or finish without an attempt. After a nonterminal result, the existing guard prevents self-disable; normal jobs retain self-disable. The skill now explicitly stops on the initial exact-target result. No new approval persistence or scheduler capability is implied.

The real `CreateOnce` validates the provider's 409, positive server ID and exact returned label before returning `target_exists`; malformed or mismatched responses become uncertain. Interrupted durable claims, failed claims, conversation/checkpoint saves, and reply-queue persistence failures require review. A model error after a terminal remote result requires review; a successfully processed terminal result is durably self-disabled. The existing exact-name guard retains its accepted check-then-create duplicate risk after an uncertain timeout, and handoff is never replayed.
