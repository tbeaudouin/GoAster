# One-shot migration machine creation

On the migration-enabled public web service, send `POST /api/migration/create` over HTTPS. This route is independent of the legacy `/migration/v1/machines/*` prepare, create and status protocol. It has no operation status, deduplication, or retry record. Every request can create another billable server. The caller must coordinate attempts and reconcile uncertain outcomes with Hetzner manually; never automatically repeat a create request.

Generate a fresh 32-byte cryptographically random secret for each request, encode it as unpadded base64url, and send `Authorization: Bearer <secret>`. This is the owner handoff credential, not an independent service access credential: possession of a valid Hetzner token authorizes provisioning. Generate a fresh Ed25519 login key pair and keep its private key for the browser setup. Send `Content-Type: application/json`:

```json
{"hcloud_token":"<HCLOUD_TOKEN>","server_type":"cx22","locations":["fsn1"],"login_public_key":"ssh-ed25519 <canonical-public-key>"}
```

`locations` is optional; an empty array or omission permits any compatible available location. A nonempty list is strict; entries must be unique valid location names. The exact requested server type is required. The service determines its x86 or ARM architecture from Hetzner and validates the matching Ubuntu 24.04 system image, type and location before provisioning. Public IPv4 is enabled; IPv6 and private networks are not requested. There is no quote or price cap. No fields beyond those shown are accepted.

A successful response has HTTP 201 and `creation_state: "created"`, `attempt`, `server_label`, `server_id`, `ip`, `location`, `expires` (Unix seconds), and `setup_url`. The URL contains the owner secret in its fragment; treat the entire URL as a credential and open it privately. Upload the matching private key in the browser. The existing provider identity verification, callback host key, pinned SSH, and shared authorization flow remain in force. The operation identity is generated by the service solely for the expiring handoff.

Errors have `creation_state` and `error: {"code", "stage", "http_status", "provider_code"}`; `provider_code` is present only when safely available. `not_created` means no server-create request was dispatched. `no_capacity` identifies a valid type and image with no available permitted location (HTTP 409). An SSH key may already have been registered with Hetzner even when the server is `not_created`. `unknown` means the create response was lost or unusable; inspect the Hetzner project before any new request. `created` on an error means Hetzner confirmed a server but setup handoff could not be completed; the response includes any known `server_id`, `ip`, `attempt`, `server_label`, `location`, and `expires` for manual reconciliation. The caller must also treat a lost HTTP response as unknown. Do not log tokens, bearer secrets, request bodies, private keys or setup URLs.

Validation is offline: `go test ./...` and `go vet ./...`. Provider calls in tests use fakes or local HTTP test servers; no cloud credentials or production services are required.
