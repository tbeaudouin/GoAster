## Findings

- **Required name and early rejection:** `internal/chat/migration_tool.go` adds `server_name` to the schema's required fields. The schema declares a string; runtime validation enforces the exact `^goaster-migration-[0-9a-f]{16}$` format. Missing, empty, whitespace-only, null and malformed names are rejected before the immediate `Create` callback. Scheduled rejection notifies the transport callback to stop the attempt, rather than dispatching provisioning. `cmd/goaster-agent/generic_cron.go` also validates the exact format before claiming execution or calling its create callback.
- **One-shot enforcement before effects:** `validateOneShotRequest` requires the same exact format, and `CreateOnce` calls it before completing options, resolving the recipient, preparing handoff, loading the token, generating login material or sending HTTP. The validator checks exact length, prefix and lowercase hexadecimal characters without trimming or substituting a name. Both production immediate and scheduled create paths in `cmd/goaster-agent/main.go` use `CreateOnce`.
- **Exact Web request and response:** The outbound payload always includes the unchanged requested `server_name`. A successful response must return that exact name as `server_label` before handoff can proceed. A mismatch retains the created state, reports failed handoff, logs the failure and sends no setup material. The existing-target response also requires the exact requested label and remains a terminal non-creation result. Contract documentation consistently requires the name for both immediate and eventual requests.
- **Approval and retry guidance:** The bundled skill now generates and presents the exact random name before the single conversational approval, together with the type, locations, price information and immediate/eventual choice. It then reuses the approved name in an immediate create or the ordinary cron message. AUTH, README and migration documentation agree. Packaging assertions cover the updated required-name wording in source and installed starter assets.
- **Preservation:** The stricter mandatory check is confined to the active one-shot path; the shared legacy validator retains its prior optional-name behavior, preserving historical request shapes. No stored-record conversion, retired-runtime activation or replay was added. Paired-owner validation, separate private URL/key delivery, secret handling and diagnostic ownership remain intact. Cron still permits one invocation per eligible turn and retries a create outcome only for explicit `not_created` plus `no_capacity`; existing-target, success, uncertainty and handoff/lookup failures remain terminal. No new pointers or approval machinery were introduced by this change.

## Evidence and limitations

Read the added immediate and scheduled tool rejection cases and one-shot rejection cases for omitted, empty, blank, null and malformed names. The one-shot tests assert no recipient/token/handoff callbacks on invalid input; source ordering also establishes rejection before key generation and HTTP. The offline success test checks the exact outbound name, and the wrong-returned-name case checks failed handoff with no delivery. Updated Telegram fixtures retain the transport-error diagnostic exercise. Existing real-session cron tests cover no-capacity retry and terminal outcomes, but identical mocked requests do not establish independent approval binding. The new invalid-name scheduled tests use a rejection callback; they do not directly exercise the real cron executor's invalid-name guard end to end. These are coverage limits, not observed defects.

The accepted architecture deliberately keeps name, type and location terms instruction-led. A model can supply another syntactically valid name or different valid terms; there is no independently bound approval record, persisted name binding or custom scheduler state enforcing their identity across attempts. This existing limitation is accepted within this review's scope and is not a request for additional machinery.

Actual provider behavior, paired Telegram delivery and installed user-owned guidance were not exercised. Existing installations require their separate guidance reconciliation/rollout; packaging assertions do not prove deployed adoption.
