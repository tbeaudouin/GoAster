# Cron self-disable review — 2026-11-17

**Verdict: changes requested.** The scheduled self-disable identity is bound to the live scheduler owner, and tool visibility is checked at both definition and dispatch. However, scheduled turns can create additional jobs, approved migration values are not bound to execution, and a successful self-disable can be undone by retry finalization. These gaps leave the requested capacity-only and self-disable guarantees dependent on model behavior.

## Findings

1. **High — A scheduled turn can add jobs before its first migration call.** The skill prohibits adding any job from a scheduled turn (`skills/goaster-migration/SKILL.md:57`), but the only mutation guard in `internal/chat/cron_tool.go:247` is conditional on `started()`. Before the first migration invocation, the `add` branch at `internal/chat/cron_tool.go:250` accepts an ordinary job, and a non-migration scheduled turn has no such guard at all. A model can therefore create another recurring job, including one that later attempts a migration, even though the prompt says not to. Reject `add` for every genuine scheduled turn at the tool boundary, independently of whether a migration has started; retain any separately intended management operations. Test both before and after create, including a non-migration scheduled turn.

2. **High — Scheduled create arguments are not bound to the approved literal job.** `internal/chat/migration_tool.go:123` validates only the syntax of the model-supplied name and type, and `internal/chat/migration_tool.go:133` forwards those supplied fields. `cmd/goaster-agent/generic_cron.go:136` checks the name format, while `cmd/goaster-agent/generic_cron.go:141` checks that the persisted job itself still matches the claimed job, not that the requested name, type and strict locations match its approved values. Thus a model error or injected job text can create a different valid server or widen locations under the original approval. Store the approved request as structured durable data and compare the actual create request to it before claiming or creating; reject mismatches and test each field, including omitted versus empty locations as appropriate. The immediate approval and one-job creation are likewise prompt-driven (`skills/goaster-migration/SKILL.md:38` and `skills/goaster-migration/SKILL.md:50`), so an enforceable one-approval/one-job guarantee needs a durable workflow binding rather than natural-language instructions alone.

3. **Medium — Retry finalization can reverse a successful self-disable.** `internal/scheduler/scheduler.go:1085` durably sets `Enabled` false, but a claimed migration that returns exact no-capacity causes `cmd/goaster-agent/generic_cron.go:182` to return `ErrRetry`; `internal/scheduler/scheduler.go:1376` then unconditionally sets `Enabled` true when the claim was owned. If the model calls `cron_disable_self` after the no-capacity result, the tool reports success and the job nevertheless runs again. Record an explicit self-disable separately from the temporary disable used by `ClaimExecutionMatching`, and make finalization honor it even on `ErrRetry`. Cover the sequence through persistent reload and subsequent due runs.

4. **Medium — Ordinary one-run jobs can acquire migration retry behavior.** `cmd/goaster-agent/generic_cron.go:215` identifies migration jobs solely by private origin, 1800-second interval and `MaxRuns == 1`; it does not identify a migration-specific job or an approved request. Any pre-existing ordinary job with that shape receives the migration create capability and can be rearmed indefinitely on no-capacity (`cmd/goaster-agent/generic_cron.go:147` and `internal/scheduler/scheduler.go:1376`), despite its one-run configuration. Persist an explicit migration workflow marker and approved request, with a deliberate compatibility path for existing migration jobs; leave unrelated `max_runs: 1` jobs under their existing semantics. Test legacy ordinary jobs and legacy migration retry jobs separately.

## Scope and checks

This is a static review of the uncommitted changes and relevant call paths; no code was changed, tests executed, network contacted, or secrets/runtime/cloud state accessed.
