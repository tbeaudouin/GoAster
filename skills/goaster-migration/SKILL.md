---
name: goaster-migration
description: Create now or schedule one exact new Hetzner Cloud server and deliver its setup privately.
---

Use `goaster_migration` only in a paired private Telegram conversation. This workflow creates a new Hetzner Cloud server only. It does not manage existing servers or other providers.

Before discussing server choices, check whether `HCLOUD_TOKEN` is available through the configured protected environment without displaying or exposing its value. Follow `goaster-env`: read protected `<real user home>/.goaster/env` first, then use process `HCLOUD_TOKEN` as fallback. If protected settings cannot be read, fail closed with a safe configuration error; do not bypass them. If the token is absent, tell the user in the paired private Telegram conversation to:

1. Send `/get-env` to download `goaster.env`.
2. Edit that file locally to add `HCLOUD_TOKEN`.
3. Attach the edited `goaster.env` with `/env` in the same message.
4. Review the preview and reply exactly `ACCEPT`.

Never ask the user to paste a secret in chat. After acceptance, recheck the credential through the protected environment. Token presence alone does not prove that it authenticates successfully.

Then use internet search/fetch of the official public Hetzner Cloud catalogue to review current server types, specifications, and rough public pricing: [Cloud](https://www.hetzner.com/cloud/) and [Cost-Optimized](https://www.hetzner.com/cloud/cost-optimized/). Identify the source, currency, date checked, and VAT basis when shown. If a price is missing, continue without it. Mention optional IPv4 costs separately only when the public page shows them; do not invent an amount or make another query a requirement. Public listings, prices, and availability badges are indicative snapshots, not guaranteed live capacity. A temporary unavailable badge does not mean a type is retired.

Prefer a fitting cost-optimized CX or CAX type first, based on the user's size requirements and workload. Respect architecture: CX is x86 and CAX is ARM; confirm the user's software supports ARM before proposing CAX. There is no blanket preference between CX and CAX. Consider CPX only when the user explicitly asks for or chooses it. Never switch to CPX automatically when CX or CAX is unavailable. Before asking for approval for either an immediate or eventual creation, generate one cryptographically random target name with the normal shell tool, for example `printf 'goaster-migration-'; od -An -N8 -tx1 /dev/urandom | tr -d ' \n'`. Confirm it matches `^goaster-migration-[0-9a-f]{16}$`. Explain the selected type, exact proposed name, optional strict locations, rough public price, and whether creation is immediate or eventual, then obtain one explicit conversational approval for that exact name and choice. No separate naming approval or workflow is needed. Do not substitute a name or type after approval. An omitted or empty location list permits any compatible location; a nonempty list is a strict allowlist and is never widened. There is no target price or price cap.

Use the normal public search/fetch tools for catalogue discovery and rough pricing. The protected provider token is used only for the one-shot create request; the Web service performs live availability and provider sequencing. Public discovery and pricing must not become a required authenticated gate or approval field. Keep `hetzner-auth` safeguards for any other authenticated request.

After explicit conversational approval in a paired private Telegram conversation, reuse the exact approved name. For an immediate request, call `goaster_migration` action `create` with that `server_name`, type and locations. For an eventual exact request, add an ordinary cron job with `every_seconds: 1800` (1800 seconds) and `max_runs: 1`; its message must explicitly include the same exact name, approved server type and locations and instruct each run to call `goaster_migration` action `create` with that same `server_name`, type and locations. Every immediate and scheduled create supplies the same approved fixed name. Tell the owner the exact name, that this creates a server automatically, and that waiting may take days; do not promise a time. The protected one-shot Web endpoint performs public admission and rate bookkeeping first, then the read-only exact-name lookup before capacity, key, or billable create work on every attempt. This remains an instruction-led conversational workflow, not an independently bound approval record: the model must follow the visible instructions, and there is no persisted name binding, scheduler custom state, separate naming workflow, or other approval enforcement mechanism.

For a scheduled job, retry only when the one-shot result explicitly has `creation_state: not_created` and `code: no_capacity`. A `target_exists` result stops normally: no new server was created, and setup or SSH key recovery is not implied. A delivered success stops the job. A created server with failed or partial handoff delivery, a provider lookup failure, a timeout or unknown result, and every other result stop the job for safe manual review; do not replay or recreate after success, uncertainty, or a process crash. Report the safe outcome privately.

If a later interactive attempt follows a terminal or uncertain result, warn that a duplicate could incur extra bills, recommend optional account inspection, and obtain one clear fresh approval. Do not require account inspection, local attempt history, or repeated confirmation.

The setup URL is a separate clickable private message. The SSH private key is a separate directly uploadable attachment named `id_ed25519` containing only key bytes and no explanatory text. Revalidate the paired owner before each delivery part. Never expose the URL, key, or token to the model, tool output, logs, or local persistence. If delivery is partial, report it honestly and never recreate automatically.

Only a real claimed private cron job with this interval and run limit can make one scheduled create call per turn. Scheduled turns cannot add further jobs. Normal scoped cron management remains available. This runtime has no migration-specific monitor or operation store; existing files from older installations are untouched and are not read, migrated, or resumed. The owner completes setup using the private handoff and existing web verification flow.
